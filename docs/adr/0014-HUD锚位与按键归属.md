# HUD 锚位与按键归属

玩家状态读数一律锚在下半区：**气血条贴屏幕下缘通栏**（厚 18px，左端「气血」、右端「当前 / 上限」，挨咬那一瞬整条提亮，三成以下加一道呼吸的朱砂描边）；**琴心蓄能沿左右两条屏幕边缘竖直生长**（宽 20px，自下而上充能，十分格刻线，槽顶印整数读数「琴心 已蓄/30」，过 82% 起呼吸，满格即放）。顶边那条 8px 通栏血条与左上角 240×9 的蓄能槽不是叠一份，而是搬家——旧锚位整个撤掉。同时**游戏消费的按键归游戏**：方向键、空格、PageUp/PageDown/Home/End 在 `keydown` 里 `preventDefault`，唯一例外是焦点落在原生表单控件上（设置里那条音画偏移滑条要靠方向键做原生微调，抢过来反而不能用）。

理由：玩家的视线全程钉在下落区与判定线上（判定线在 0.8 屏高，键位标签在其下方 24–34px），屏幕最顶边根本不在视区里。旧版把血条画成顶边 8px 的一条细芯、把琴心槽收在左上角 240×9 的一小块颜色深浅——玩家玩了两周，问的是「我的血条在哪」「特殊技能的进度看不到了」。这不是调色或加粗的问题，是锚位选错了：条画在视区外，等于没画。竖直条比横条更容易被周边视觉捕获（长轴与视线的主要移动方向垂直，两侧边缘对比最强），左右各一条让两侧的余光都能接住；两个量都给整数读数，因为「还剩几格、还差几击」是玩家真正要决策的信息——颜色深浅只能表达「大概一半」。第二条是同一类错误的反面：菜单自己消费方向键，却把键位的**浏览器默认行为**（滚动文档、空格翻页）留给宿主——`html,body{overflow:hidden}` 在 Chromium 里能挡住滚轮路径，但挡不住所有宿主（iframe 嵌入、矮窗口、把 overflow 当视觉裁剪的实现），而这一行 `preventDefault` 不依赖宿主行为。

后果与边界：状态区占的是屏幕下方 20% 带的边角与两侧边缘空档，不进入键位列（竖槽距边缘 16px、宽 20px，最窄 800×600 也不压轨道；气血条与键位标签至少留 28px）；矮窗口里气血条的下沿被「判定线下方 58px」钳住，不会压到键位标签。HUD 只读不改：血量、咬线、充能速率、伤害、判定窗口一个数值都没动（ADR-0013 的窗口仍是唯一定义处）。读数的分子直接取模拟器的整数计数 `qinxinHits`，不拿 `qinxinGauge × 30` 反乘回来——浮点取整会时对时错，而「还差几击」这种数不能错。结算画面与曲库（backdrop 分支）仍不画 HUD。以后要加新状态（例如中毒层数），按同一规则落到这两条锚位上，不许再加回顶边。
