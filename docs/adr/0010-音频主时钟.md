# 音频主时钟

游戏时间轴的唯一权威是 `audioContext.currentTime`：判定、连击、谱面推进等一切"何时"都以音频时钟为准；`requestAnimationFrame` 只负责把当前时刻画出来，不定义时刻本身。按键事件在壳层读到的瞬间被盖上音频时钟时间戳，交给纯核心模拟器判定（模拟器对时钟零依赖，时间一律注入，故 Seam 1 测试喂固定值即可）。声音分两类调度：已知未来时刻的声音（倒计时、后续工单的伴奏）经 lookahead 调度器提前注册到 Web Audio 的采样级时间线（25ms 轮询、120ms 视野）；玩家触发的琴声属事件驱动，按 `now + ε` 即时调度，ε 仅用于把 `start()` 放进时间线的近未来以避免爆音。

理由：`currentTime` 由音频硬件时钟驱动、按渲染块（128 采样，44.1kHz 下约 2.9ms）步进，是唯一与"玩家实际听到什么时刻"对齐的钟；rAF 时间戳与 `performance.now()` 都与声音播出脱钩，若用来计时，等于把 ±50ms 的判定窗口架在两套不同步的钟上——判定公平性无从谈起。方案参照 Chris Wilson《A Tale of Two Clocks》（lookahead 调度）与 Sonoport《Understanding the Web Audio Clock》（时钟精度特性）。

后果：没有 AudioContext 就没有游戏时间——待开始画面不计时，恰与浏览器自动播放策略要求用户手势起步相合；切换标签页导致的时钟停走，交给暂停机制（后续工单）处理；音画偏移校准（工单 06）实现为"渲染相对主时钟的整体偏移"，全项目只有这一处可调，不会出现第三套钟。

**增补（2026-11-01，工单 21）**：调度队列的**生命周期跟着画面走**——终局画面（结算）出现时，引擎丢弃全部未到期任务并把音乐轨在 0.35 秒内淡出；开新局与重放演奏时把音乐轨恢复到设置音量。理由是伴奏这类「整首一次性排完」的声部一旦没人清队列，输了以后会继续在结算背后演奏到曲末（实测：结算后的 6 秒里仍有 3 次发声、间隔恒定 2 秒）。淡出而不是硬切，因为正在响的采样被瞬间掐断会爆音；恢复只在开新局/重放时发生，避免「第二局静音」这种反向故障。
