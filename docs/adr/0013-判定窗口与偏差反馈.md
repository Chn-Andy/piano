# 判定窗口与偏差反馈

判定只有一个量：**|按键时刻 − 音符时刻|**。音符时刻是「音符中心与判定线重合的那一刻」（零点），按键时刻取按下那一瞬的音频主时钟（ADR-0010）。偏差 ≤ 50ms 判**完美**、≤ 120ms 判**良好**、超出良好窗判**失误**；边界含等号，与早/晚方向无关、与连击/谱面密度/异色无关。三档的后果：完美 ×1.0 伤害、良好 ×0.7 伤害（两者都 +1 连击），失误无伤害、断连击、剑气扑空。两条口径一并钉死：一颗音符只判一次（早于良好窗的按键不消耗音符，音符继续等，那次按键只是空按）；失误由**时间**判出（音符等到良好窗过期才落 Miss），不由按键判出。判定一律在纯核心（`Simulator.keyDown/tick`）里算，常量集中在 `config.JUDGMENT_WINDOWS`，那是唯一定义处。

偏差必须**可见**：判定闪示在「完美/良好」下面补一行「早 12 / 晚 43」的小字，结算画面给整局的平均偏差（正=偏晚）并在 ≥8ms 时直接指路「把音画偏移调到 +N」。判定线上另画两道墨晕，把窗口折算成屏幕厚度：完美带 ±17px（50ms × 340px/s 下落速度）、良好带到 ±41px。

理由：这就是原文「滑块在线的中间附近才是完美」的可执行表述——中心 = 0 偏差，越靠近中心档位越高。但**窗口在屏幕上是看不见的**：340px/s 下完美带只有 34px 高，比一颗音符（26px）还窄，良好带也只有 82px，而玩家没法用肉眼分辨「我这次是差了 30ms 还是 90ms」。不给数字，玩家只能记住「刚才大概感觉对/不对」，学不会收敛，也永远不会想到问题出在设备延迟上——那正是设置里那条 ±150ms 的音画偏移存在的意义（正值 = 判定提前，补偿「按键总是偏晚」的设备与手感）。50ms 约 1–2 个显示帧（60Hz 一帧 16.7ms），吸收人因抖动后仍能区分「很准」与「准」；120ms ≈ 2.4 × 完美窗，中间档不苛责。

后果：判定窗口的**具体数值**仍属真实设备人工验收范畴（`docs/calibration.md` 第一节），调窗口不改反馈结构——改的是宽窄，不是「说没说清楚」。平均偏差只统计命中（Miss 没有按键，不计入），命中不足 8 颗时不报（样本无意义）。偏差反馈不参与胜负与评级计算，它只是把已经有的事后数据说出来：评级用精度 `(完美 + 0.6×良好) / 总音符`（`rating.ts`），那仍是唯一的表现总结（ADR-0008 无独立分数系统）。
