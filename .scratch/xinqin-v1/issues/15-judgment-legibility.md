# 15: 判定口径说清楚（完美/良好到底怎么判、偏差要看得见）

**What to build:** 用户提问：「到底完美、良好这个是怎么判定的？以前玩劲乐团是要在滑块在线的中间附近才是完美，现在不知道是怎么判定的——这是整个游戏的核心，一定要定义清楚。」判定本身早就实现成 `|按键 − 音符| ≤ 50ms = 完美 / ≤ 120ms = 良好`（`config.JUDGMENT_WINDOWS`），但**只有代码里有，游戏里看不见**：判定闪示只印「完美／良好」四个字，不说是早了还是晚了、差多少毫秒；判定线是单纯一条枯笔，完美带（±17px）肉眼无从分辨；结算只有评级字母，没有精度与平均偏差——玩家无法从任何一处得知自己「为什么是良好」，也就无法学会收敛，更不会想到去调音画偏移。本票把判定写成一等公民：定义进代码注释与 ADR，偏差进闪示、判定带进画面、平均偏差进结算并直接指路偏移值。

**Blocked by:** 06（音画偏移与窗口定标）；参考 ADR-0010、ADR-0013

**Status:** resolved

## Comments

**2026-10-30 · 开票与关票同批**：

### 1. 当前的判定（原文＝代码，没有第二套语义）

| 偏差（含等号） | 判定 | 伤害 | 连击 |
|---|---|---|---|
| ≤ 50ms | 完美 | ×1.0 | +1 |
| ≤ 120ms | 良好 | ×0.7 | +1 |
| > 120ms | 失误 | 无（剑气扑空） | 归零 |

- 零点 = **音符中心压在判定线**上那一刻（`y = judgeLine − 剩余时间 × 340px/s`），所以「滑块在线的中间附近」在这里就是「偏差接近 0」。
- 按键时刻取按下那一瞬的音频主时钟；偏差与早/晚方向无关（早 30ms 与晚 30ms 同为完美）。
- 早于良好窗的按键**不消耗音符**：音符继续等，那次按键是空按（钢琴会响一声，但没有判定）。
- 失误是**时间**判出来的：音符等到「时刻 + 120ms」才落 Miss，不是按键判出来的。

### 2. 为什么「感觉说不清」

窗口在屏幕上的实际厚度：50ms × 340px/s = **17px**，120ms = 41px。一颗音符高 26px——完美带比音符本身还窄，良好带也只有音符的 1.6 倍。也就是说，即便玩家死盯判定线，也**分辨不出**这次是 30ms 还是 90ms。判定不带数字，就等于要求玩家靠直觉收敛，反馈环路是断的。

### 3. 这一版补的三处可见性

1. **闪示小字**：`完美` 下面一行 `早 12` / `晚 43`（0 记「正点」），Miss 不显示（没有按键）。
2. **判定带墨晕**：判定线上叠加两道极淡的渐变墨晕，上半个带＝按早了（音符还在线上方），下半个带＝按晚了（音符已过线）。
3. **结算指路**：`精度 87.3%` + `按键平均偏晚 23ms —— 可在设置里把音画偏移调到 +23`（|平均| < 8ms 时改口说「节奏稳」；命中 < 8 颗不报）。

### 4. 没有动的东西（有意为之）

判定窗口的数值（50 / 120）**没有改**——`docs/calibration.md` 的规矩是「无真实设备试玩证据不动窗口」。本票只把已有的事实说清楚。如果试玩后觉得完美带太窄/良好带太宽，改 `JUDGMENT_WINDOWS` 两个数即可，反馈结构不用动，像素厚度会自动跟着变（渲染层是从常量与 `FALL_SPEED` 折算的）。
